# 自动交易每日闭环审计

用于回答“系统是否能自动发现买卖点、下单、飞书通知并完成每日闭环”，以及解释盘中常驻交易进程为何运行。

## 审计原则

不能只看 cron 的 `last_status=ok`，也不能只看脚本注释或服务处于 running。必须穿透验证：

`信号产物 → 候选流水 → 风控审批 → 订单报送 → 订单/成交回查 → 飞书通知 → 收盘 outcome → 策略学习`

任何一段只有代码而没有运行产物，都只能判定为“具备能力，尚未验证”。

## 1. 常驻进程的判定

盘中守护脚本由 systemd 常驻时，区分两种状态：

- **进程常驻**：服务全天 active，避免开盘冷启动和 cron 延迟。
- **业务活跃**：只有脚本内交易时段守卫返回 true 才查行情、判信号或下单。

检查四项：

1. unit 的 `ExecStart`、`Restart`、`WorkingDirectory`。
2. `is-enabled` 与 `ActiveState/SubState`。
3. 脚本主循环的 sleep 周期和交易时段函数。
4. `NRestarts` 与 journal 中的 SIGKILL/异常；自动恢复不等于从未故障。

报告时应明确：“一直运行”不等于“一直交易”。

## 2. 自动交易能力的实证标准

至少收集一条完整真实链路：

1. 扫描器输出结构化 candidate，含稳定 `candidate_id`。
2. 执行器日志显示该 candidate 被消费。
3. Risk MCP 返回 approved/reduced 或明确拒绝。
4. Exec MCP 返回真实 `order_id`。
5. `get_orders`/`get_today_trades` 或历史订单归档能回查状态。
6. intent 文件与 candidate_event 已写入。
7. 收盘 review/outcome 能关联同一 candidate。

只有扫描器写“已推送”“已注入”不能证明成交；只有当前持仓也不能证明是哪条策略产生。

## 3. 飞书通知语义

严格区分：

- **候选通知**：发现机会，不代表批准或下单。
- **订单报送通知**：取得真实 `order_id`，表示已进入券商柜台。
- **成交通知**：订单状态已回查为 FILLED，或成交接口存在对应 trade。
- **失败通知**：风控拒绝、注册失败、报单失败、撤单或取消。

禁止使用默认字符串“已提交”掩盖空响应。只有真实 `order_id` 才能写“已报送”；没有成交回查时，标题不得写成确定成交。

报单失败后，如果脚本存在本地冷却锁，应清除该锁，让下一轮可以自愈重试；但禁止无限重试已被风控明确拒绝的订单。

## 4. 每日闭环的六段核验

### A. 盘前

- 市场状态机、策略参数和跨日日期已刷新。
- 盘前观察池/候选文件存在且可解析。
- MCP 9001/9002/9003健康。

### B. 盘中发现

- 竞价、龙头、题材、回踩、持仓防守等扫描任务按设计频率运行。
- 无候选时要有 run marker 或过滤原因，不能把脚本未产出误报成市场无机会。

### C. 风控与执行

- 市场状态、策略熔断、连板高度、追高、方向一致性、仓位、T+1均真实参与阻断。
- 多个可下单入口必须列清楚，确认是否共享统一执行函数和流水格式。

### D. 通知

- 候选、报单、成交、拒绝的消息类型不可混淆。
- 心跳消息必须依据实时阈值生成；禁止无条件宣称“所有持仓安全”。

### E. 收盘复盘

- 对 candidate 结算 MFE、MAE、close PnL、B浪等级和退出原因。
- 当前持仓、订单、成交、candidate_event 数量应能对账。

### F. 策略进化

- 学习引擎只能消费真实定义范围内的样本。
- “执行笔数”必须由订单/成交、candidate_event 和 intent 归档交叉核验。
- 若进化报告写执行0笔而账户/订单显示有成交，应判定为统计口径缺口，不得据此调整策略。

## 5. 双执行入口风险

当 `direct_executor` 与盘中高频守护脚本都能下单时，重点检查：

- 是否都生成 `candidate_id` 和 `intent_id`。
- 是否都经过相同的铁律门禁和Risk MCP。
- 是否都写统一 candidate_event 与 intent 归档。
- 是否都执行订单回查和飞书通知。
- 是否存在同票重复下单、方向冲突或统计漏记。

长期推荐架构：高频守护负责触发和生成 candidate，统一执行器负责审批、报单、回查、归档、通知；紧急卖出可保留快速通道，但应复用同一执行函数和事件协议。

## 6. 测试与生产状态隔离

交易测试可能读取真实 `breaker_state.json`，导致“应放行”的测试因生产策略熔断而失败。这不是代码回归，也不能通过清空生产熔断让测试变绿。

处理方式：

1. 专项测试把配置目录、熔断文件、feedback目录 monkeypatch 到临时目录。
2. 报告测试结果时区分：本次修改专项测试、生产状态污染的旧测试、真正回归失败。
3. 测试禁止修改真实持仓、订单、熔断和策略参数。

## 7. 报告定性模板

最终结论分四级，避免笼统写“已闭环”：

- **能力存在**：代码和配置具备功能，但无运行证据。
- **主链已验证**：至少一条发现→下单→回查→复盘链真实跑通。
- **核心闭环可运行**：主链及日常调度可运行，但部分支路或统计仍有缺口。
- **全链闭环已验证**：所有启用入口、通知、复盘、学习均完成跨源对账，无未验证支路。
