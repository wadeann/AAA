# A股行情 MCP 多源聚合、交叉核验与健康检查

## 适用场景

当出现以下任一情况时使用本流程：

- 用户指出连板高度、现价或涨跌幅与报告不符；
- 单一数据源额度耗尽、超时、返回空数据或字段错位；
- 需要把新浪、腾讯、东方财富、同花顺等行情源补充进 Intel MCP；
- MCP 工具返回值与本地策略脚本、自建天梯或官方直连报价冲突；
- 需要判断“没有买点”究竟是市场结论，还是数据源失效导致的空候选。

## 第一原则：先验证数据，不先解释市场

用户纠正关键行情数据后，禁止继续基于原错误数据推演。必须立即：

1. 重拉至少两个独立实时源；
2. 对照本地策略脚本或持久化底表；
3. 明确指出哪个接口错误、哪个来源可信；
4. 再修改代码或交易结论。

尤其是连板天梯：若通用 MCP 工具显示“最高仅首板”，但盘中脚本显示6板，不得直接判定退潮。先检查工具是否进入了降级路径、是否丢失昨日身位、是否把所有涨停股默认成首板。

## 推荐架构

在 Intel MCP 内使用统一 `MarketAdapter` 接口，每个来源只负责：

```python
class MarketAdapter:
    @property
    def source_name(self) -> str: ...
    def fetch_quote(self, symbol: str) -> StockQuote | None: ...
```

统一输出 `StockQuote`：

- symbol / name
- price / prev_close / open / high / low
- volume / amount
- change_pct / amplitude
- source / fetched_at
- 可选估值字段

推荐实时行情源：

1. 腾讯财经：低延迟主源；
2. 新浪财经：独立交叉验证；
3. 东方财富 push2：估值字段和补充源；
4. 同花顺公开分时接口：与问财 API Key 独立，不消耗问财额度。

## 两类 MCP 工具应分开

### 1. 低延迟顺序降级

`query_data(symbol)`：依次尝试各适配器，首个有效报价即返回。适合普通查询和高频脚本。

### 2. 多源共识核验

`query_multi_source_quote(symbol, tolerance_pct=0.2)`：查询全部数据源并返回：

- `consensus_price`
- `source_count`
- `agreeing_sources`
- `outlier_sources`
- `max_deviation_pct`
- 每个来源的完整独立报价

共识计算建议：

1. 取各源价格中位数；
2. 与中位数偏差不超过阈值的来源进入共识组；
3. 共识价取共识组均值；
4. 其余来源标记为异常源，不污染最终价格。

关键交易价格、涨跌停判断、用户指出数据冲突时，必须用多源共识工具，不得只调用顺序降级工具。

### 3. 数据源健康检查

`market_source_health(symbol="600519.SH")` 应逐源返回：

- `ok`
- `latency_ms`
- `quote`
- `error`

单源失败必须隔离，不能让整条链路失败。

## 同花顺公开行情接口

可用的日内快照形式：

```text
https://d.10jqka.com.cn/v6/line/hs_{code}/01/today.js
Referer: https://stockpage.10jqka.com.cn/{code}/
```

返回 JSONP，核心字段：

- `7`: open
- `8`: high
- `9`: low
- `11`: price
- `13`: volume（股，统一模型中按接口语义转换）
- `19`: amount
- `name`: 股票简称

注意：该接口未直接给出昨收时，不要伪造 `change_pct` 和 `amplitude`；应保持0/空，或由另一可信源补齐。

## 东方财富适配注意事项

- 沪市 `secid=1.代码`；深市与北交所通常使用 `secid=0.代码`；
- 优先 HTTPS，并轮询多个 push2 子域；
- 必须使用统一 HTTP client，便于超时、连接池和测试注入；
- 返回空数据、502或超时时只标记该源失败，继续其他来源；
- 东财当前不可用是健康状态，不应写成永久负面结论。

## 严禁：用证券代码相邻关系推断同行业

证券代码 ±N 与行业、题材没有可靠关系。不得用“以涨停股代码为中心±30码”构造所谓同行业候选池。该方法可能把完全无关股票标成同板块，属于数据语义错误。

若问财和 TDX 选股额度都耗尽，正确降级顺序是：

1. 使用已有板块成分股缓存或权威行业映射；
2. 使用独立公开板块成分接口；
3. 只输出已有、可验证的条件预案；
4. 明确标记“行业候选数据源不可用”，不要伪造同行业候选。

## 高频公开行情 + 低频问财的职责分层

为兼顾实时效率、信息密度和免费接口的可持续性，不要让问财承担秒级报价，也不要对公开行情源无缓存地轮询。

### 数据职责

- **公开行情源**：最新价、涨跌幅、OHLC、成交量额、盘口、涨停状态、批量报价和多源价格核验。字段标准、调用频繁，但必须节流。
- **问财**：几天几板、首次封板时间、行业/概念归属、竞价细节、流通市值及复杂自然语言条件。信息密度高、调用低频，结果应缓存复用。

原则：公开行情回答“现在多少钱、涨了多少”，问财回答“属于什么、为什么涨、是否满足复杂条件”。同一字段能从公开行情稳定取得时，不消耗问财查询。

### 逐源 TTL、失败负缓存与熔断

缓存和熔断必须以 `(source, normalized_symbol)` 为粒度，避免某只股票或某个上游故障拖累全部报价：

1. 给每个来源配置独立成功缓存 TTL；高频主源可短，慢源/补充源应更长。
2. 请求失败或返回空数据后写入短时**负缓存**，有效期内跳过该源，避免每轮重复等待相同超时。
3. 单源连续失败达到阈值后开启 circuit breaker；冷却期间不发请求，期满后允许探测恢复。
4. 任一成功报价必须同时清理该 `(source, symbol)` 的负缓存、失败计数和熔断状态，防止已恢复的数据源仍被错误隔离。
5. 单源失败只降低 `source_count`，不得使顺序降级或多源共识整体失败。

建议参数不是永久常量，应通过配置和测试校准。可用起点：主源成功 TTL 3 秒、辅助源 10–15 秒、负缓存 30 秒、连续失败 3 次后熔断 120 秒。

### 问财缓存和并发合并

- 缓存键应由规范化后的完整查询语句及分页参数组成，不能仅按股票代码缓存。
- 盘中使用分钟级 TTL，闭市后延长到数分钟至半小时；语义宽表无需秒级刷新。
- 相同查询并发到达时使用 SingleFlight：仅一个调用访问上游，其余等待并共享结果。
- 空结果是否缓存必须区分语义：确定性的“无匹配”可短时缓存；网络失败、解析失败不能伪装成长期零结果。

### 性能验证口径

不能只验证功能返回值，还要断言上游真实调用次数和耗时：

- 同一标的缓存期内调用 N 次，上游适配器仅调用 1 次；
- 失败负缓存期内不重复访问故障源；
- 熔断后冷却期内跳过故障源，期满后只进行一次恢复探测；
- 成功恢复后负缓存和熔断状态均清除；
- 相同问财查询并发 N 次，只产生 1 次真实请求；
- 首次请求与缓存命中耗时形成明确 Before / After 对比。

测试时间相关逻辑时注入 `time_func`/假时钟，不要依赖真实 sleep；这样可精确覆盖 TTL、负缓存和熔断边界，避免慢且不稳定的测试。

## TDD 与验证

新增适配器、节流或聚合能力时，先写失败测试：

- 每个可用来源都能被 `get_quotes()` 返回；
- 一个来源异常不会影响其他来源；
- 离群价格会进入 `outlier_sources`；
- 共识价格由多数正常源决定；
- 北交所代码能正确映射；
- JSONP/GBK/字段单位能正确解析。

上线前必须完成：

1. `py_compile`；
2. 专项测试；
3. 全量测试；
4. 真实拉取至少沪市、深市各一只；
5. 直接调用 MCP `tools/list` 确认新工具注册；
6. 直接调用 `tools/call` 检查业务响应，而不只看 HTTP 200；
7. 重启 Intel MCP 服务并通过 `/health`；
8. 若要让当前 Hermes 会话看到新工具，还需新会话或在外部重启 gateway。当前会话的工具 schema 不会动态更新。

## Before / After 证据模板

```text
Before:
- 通用天梯工具：最高1板
- 本地策略天梯：最高6板
- 问财/TDX：额度耗尽
- 报告：无买点

After:
- 多源报价：腾讯/新浪/同花顺三源价格一致
- 异常源：东方财富空响应，已隔离
- MCP tools/list：出现 query_multi_source_quote、market_source_health
- 专项及全量测试：全部通过
```

重点是证明“错误数据不再进入交易结论”，而不是只说明写了哪些代码。
