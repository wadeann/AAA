# 市场数据新鲜度与 MCP Schema Drift 排查

用于出现“市场数据不对、空天梯、0板、错误周期定调、真实候选被过滤”等异常时。

## 典型症状

- 市场状态文件的 `updated_at` 早于最新交易日，却被打法卡直接引用。
- 权威接口有涨停数据，本地 `ladder_YYYY-MM-DD.json` 却是 `cache_degraded`、空 `ladders` 或 `market_dragon={}`。
- 接口契约从 `ladders` 变为 `ladder` 后，调用成功但业务层静默解析为空。
- 盘后批量行情无返回，候选 `price` 被默认成 0，随后被“价格必须>0”过滤成无标的。
- 市场状态显示进攻，但打法文本仍出现退潮、0板、空仓等互相矛盾的信息。
- **`get_limitup_ladder` 返回 `max_height=1` 且全数组 `board_height=1`，被误读成“全场只余首板/高标全部断板”。**

## 🔴 get_limitup_ladder 的 board_height 语义陷阱（2026-09-23 实战教训）

**接口**：`mcp_intel_get_limitup_ladder(min_streak=1)`。

**陷阱**：该接口的 `board_height` 字段记录的是**当日该标的涨停计数**（当日涨停就记为 1），**不是累计连板数**。同一接口的 `ladder_summary` / `max_height` 因此会显示 `{"首板": N}` 且 `max_height=1`——**即使市场存在新华文轩4连板、泰慕士3连板等高标，只要这些高标当日仍然封板，它们就只计 1**。

**错误后果**：若据此判定“全场最高只剩首板 / 4板3板高标全线断板”，会得出完全相反的退潮结论，甚至误报“空间高标坍塌”。用户会直接戳穿“连板数据不对”。

**正确口径**：要看真实累计连板梯队，必须用增强天梯产物 `ladder_enhanced_YYYY-MM-DD.json`（由 `build_ladder.py` 在 15:28 收盘后构建，含“新华文轩 4连板 / 泰慕士 3连板”这种带连板数的完整梯队），或参考盘中看板（`intraday_hot_sector_sniper.py`）的梯队阵列输出。

**判定“是否断板”的正确方法**：不能只看 `get_limitup_ladder` 的 `board_height`。应：
1. 读取 `ladder_enhanced_{date}.json` 拿昨日真实身位；
2. 对高标调用 `query_batch_data` 看实时/收盘 `price` 与 `prev_close`，用板块自适应涨停价判断是否仍封在涨停价；
3. 断板 = 该标的价格回落脱离涨停价，且不再出现在增强天梯的对应连板层。

## 强制排查顺序

1. **时间与交易日**
   - 核对 CST 当前时间、最新有效交易日及目标预案日期。
   - 周末生成次日预案时，行情事实必须锚定最近交易日，不能把周末日期当作行情日期。

2. **检查状态文件新鲜度**
   - 检查 `market_regime.json.updated_at`、`ladder_*.json.date/data_quality`、`plan_*.json.compiled_at`。
   - 若状态日期落后于最新交易日，不得直接输出；必须刷新或明确 fail-closed。

3. **在 MCP 边界检查真实 payload**
   - 验证 JSON-RPC 无顶层 `error`。
   - 解码 `result.content[0].text` 后，打印业务 payload 的顶层 key。
   - 对关键接口兼容已知契约别名，例如 `ladder` 与历史 `ladders`；调用时显式传 `date`，禁止依赖“最新”隐式回退。
   - **字段语义必须验证**：拿到 `board_height` 前先确认它到底是“当日涨停计数”还是“累计连板数”。两者语义完全不同，误读会直接导致断板/退潮的假判断。

4. **检查落盘产物**
   - 刷新后必须回读 `ladder_目标交易日.json`：日期、数据质量、空间龙、各梯队数量均应非空且与接口摘要一致。
   - `cache_degraded` 空文件不得覆盖同日已有有效 live 文件。

5. **多源交叉核验**
   - 指数关键值至少使用两类权威源核对：腾讯/官方直连、通达信、问财历史收盘。
   - 核验创业板涨跌幅、全A中位数、上涨/下跌家数、涨停数、最高板与梯队分布。
   - 数值不一致时，以带明确交易日期与收盘时间的官方/直连数据为准。

6. **检查下游静默过滤**
   - 盘后实时批量行情为空时，候选价格应回退到已归档天梯的当日收盘价，而不是 0。
   - 天梯项进入 plan 时应保留 `price/turnover_rate/seal_time/break_count/amount`，避免下游失去判定依据。

7. **一致性断言**
   - 空间龙板数必须等于天梯最高非空层级。
   - `market_regime` 为高潮/启动时，打法依据不得描述为退潮冰点。
   - 若天梯非空，打法不得声称“空间龙0板”。

## 非交易日、盘前与强制运行的防陈旧数据规则

行情接口在周末、节假日和交易日前盘前阶段，可能返回最近交易日收盘快照。**响应成功和时间戳为当前时间，都不能证明业务数据是实时行情。**

1. **先查交易日，再刷新市场状态**
   - 明确返回非交易日：不得重新计算“高潮/启动/退潮”等实时状态；输出 `data_fresh=false`、开仓乘数0、仓位上限0。
   - 交易日接口不可用：继续走全量数据 fail-closed 判断，不要把“无法确认交易日”直接等同于周末。
   - 非交易日防守结果可以继承上一交易日事实字段供复盘展示，但必须覆盖状态为“非交易日”，禁止据此开仓。

2. **盘前量能不可按盘中线性投影**
   - 09:30前的指数成交额很可能仍是上一交易日值；不得用 `240/max(15, elapsed)` 将其放大成当日全天预测。
   - 竞价阶段应单独使用竞价金额；至少到09:35后才允许盘中成交额投影。

3. **`--force` 只用于诊断，不得穿透交易时段门禁**
   - 强制运行可以展示最近交易日天梯和板块结构。
   - 非交易时段必须跳过买点筛选、候选生成、仓位建议和交易触发。
   - 输出中应明确是历史/诊断看板，不能称为实时盘中买入信号。

4. **分析来源必须真实披露**
   - 当前主模型和本地确定性脚本生成的报告，标题使用 `Hermes`。
   - 只有当前请求明确调用 AGY/Antigravity 且报告确由其产出，才允许标注 `Antigravity` 或“分析来源：AGY”。

## 个股四维共振的证据完整性

1. **MA均线不能冒充缠论结构**
   - “站上MA5”只能进入技术/量价维度，不能写成缠论得分或买点。
   - 缠论维度必须实际运行：包含处理 → 分型 → 笔 → 线段 → 中枢 → 背驰 → 买卖点。
   - 短线分析至少使用100根30分钟K线；不足时写“未计算缠论结构”。

2. **缺失维度应重新归一权重**
   - 没有缠论、资金或筹码证据时，不得给默认中高分，也不得把“未计算”当成利空打0后直接压低总分。
   - 从总权重中剔除缺失维度，对已获得的有效证据重新归一；同时在结果中披露缺失项。

3. **禁止个股和龙头硬编码**
   - 不得用股票代码专属 `if` 将某票强制归入历史题材。
   - 板块归属必须来自实时公司资料/行业概念与当日 `sector_matrix` 的名称匹配。
   - 板块未查到哨兵龙头时保持空值，严禁填入历史案例中的“默认龙头”。

4. **板块资金0值与缺失必须区分**
   - 字段未返回、名称未匹配或解析失败时写“资金数据缺失/未匹配”。
   - 只有源数据明确返回0时，才能显示“净流入0”。

## TDD 回归用例

修复前先写失败测试，至少覆盖：

1. Intel 返回 singular `ladder` 时能生成真实天梯。
2. 请求显式携带目标交易日期。
3. 天梯中价格和盘口字段完整传入 plan。
4. 批量行情为空时，使用归档收盘价，真实候选不被静默过滤。
5. 编译后空间龙、模式和打法文本互相一致。
6. **`get_limitup_ladder` 的 `board_height=1` 不被误判成“全场首板/高标断板”，真实连板梯队仍从增强天梯恢复。**

## Before / After 证据模板

- Before：状态更新时间、错误指数值、空天梯/0板、错误周期定调。
- Root cause：具体文件、字段契约或过滤条件。
- After：最新交易日、指数多源核验、梯队分布、空间龙、周期状态。
- Verification：专项测试数、语法检查、重新运行打法卡的真实输出。

核心原则：HTTP 200 或 MCP `status=success` 不代表业务数据已正确进入策略；必须检查“接口 payload → 本地归档 → plan → 打法文本”每一层。**接口字段语义也必须核实——`board_height` 这类看似直观的字段可能携带与直觉相反的契约。**
