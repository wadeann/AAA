# AGY 独立审计工作流 — 实操记录

## 核心原则：AGY审计是标准操作流程，不是可选项

用户明确要求：**"一切以AGY审核意见为准，持续最少100轮，进行螺旋上升，直到完全走通闭环。"**

这意味着：
- 发现任何系统bug/逻辑矛盾/用户指出问题时，**不要再自行分析原因后修复**——那是自我审计，用户不接受
- 标准流程只有一条路：**AGY审计→我改代码→AGY再验证→循环**
- 循环次数以AGY说"没问题"为终止，不是我说"修好了"
- 即使自我感觉"已经清楚了"，也必须走AGY审计流程

## 审计流程

```
用户指出bug/自己发现bug → 拉真实数据(交易记录/日志/cron输出/JSONL)
→ 准备审计上下文文件(/tmp/agy_roundN_context.md)
→ delegate_task启动AGY子代理审计(或agy CLI)
→ 读AGY的markdown报告
→ 按报告修改代码 → git commit + push
→ 准备下一轮审计上下文
→ 启动AGY再审计 → 重复
→ 直到AGY在下轮中说"验证通过/无遗漏P0/P1" 或用户说停
```

## 审计工具选择

### 选项A: delegate_task子代理（推荐，一般性审计）
```python
context = f"""AGY审计第{N}轮
查看 /tmp/agy_round{N}_context.md
验证文件: xxx.py第X行
...
"""
delegate_task(goal=f"AGY第{N}轮审计", context=context, toolsets=["file", "terminal"])
```
- 优势：可以做多文件验证、运行测试
- 限制：600s超时，单轮审计通常可完成2-3个文件验证
- 适用于：**验证性审计**（验证上一轮修复是否完整）

### 选项B: AGY CLI（替代方案，深度审计）
```bash
agy --dangerously-skip-permissions --print="审计prompt" --print-timeout 2m --model "Claude Sonnet 4.6 (Thinking)"
```
- 优势：无时间限制
- 限制：不能跑代码验证，不能读多文件
- 适用于：**发现性审计**（发现新问题、代码review）

### 选项C: no_agent测试脚本（兜底方案，验证特定功能）
编写Python脚本直接跑测试，输出原始结果供AGY审计用。

## 审计上下文准备格式

每轮审计前准备 `/tmp/agy_roundN_context.md`：

```markdown
# AGY第N轮审计

## 本轮审计范围
[具体文件和函数]

## 上一轮AGY发现
[引用上一轮报告中关键点]

## 我已按建议修改
[改动列表]

## 需验证的核心问题
[关键验证点列表]
```

## delegate_task内部审计的章法（2026-09-01 3轮实践经验）

实际执行3轮AGY审计的节奏和规律（使用delegate_task子代理模式）：

| 轮次 | 审计内容 | delegate_task耗时 | 发现 | 
|:----:|---------|:----------------:|:----:|
| 1 | 全管线首次审计(4个文件) | 196s/600s | 指数退避+thesis前缀 → 改2文件 |
| 2 | 验证第1轮修复+发现遗漏 | 197s/600s | P0 agy_approved不兼容+Bug D去重+P1 chan_ok → 改2文件 |
| 3 | 验证第2轮修复 | 307s/600s | ✅ 全部正确，矩阵检查无遗漏 |

**关键发现**：
- delegate_task子代理600s足够完成一轮完整审计（即使23次API调用也只用了307s）
- 每轮审计后AGY调用次数递减（22→19→13）因为范围收窄
- 第3轮AGY调用了23次工具但仍在307s完成，说明子代理的并行能力好
- **子代理比AGY CLI更好用**：CLI需要自己读文件提交审核，子代理自己有工具能逐行验证
- 审计输出包含详细的"验证了哪行代码、git diff确认等"——比CLI的更可信

## 验证AGY结论

AGY的审计结论**不一定是100%正确**。已知误判案例：

| 轮次 | AGY误判 | 实际原因 |
|:----:|---------|---------|
| 第2轮 | "candidate_update修复形同虚设（字段缺失）" | candidate_update只补充元字段无symbol/direction，不需要方向检测 |
| 第3轮 | "except:pass应加日志输出" | lean代码风格，提升效率，问题影响可接受 |

**正确的响应模式**：
- AGY指出的问题路径 → 认真考虑
- AGY说"必须按我的建议修" → 验证后判断
- 验证结果=不需要修 → 在下一轮审计上下文写明原因，让AGY签认
- **不改=不需要改的证明**，不是偷懒跳过

## 全链路集成测试验证模式

AGY审计验证通过后，仍需自己做集成测试验证。测试模式：

```python
# 测试项目
# 1. is_trade_ready 三类候选: AGY通过/仅LLM通过/普通
# 2. is_shadow_ready 完整/缺字段
# 3. normalize_intent 生成intent_id
# 4. 方向冲突检测
# 5. 风控重试逻辑（无法真实模拟，语法检查+逻辑审查）

# 验证方式：纯Python import + 调函数
python3 -c "from autonomous_trade_pipeline import is_trade_ready; test cases..."
```

## 迭代节奏

- **每轮AGY调用时间**：约3-5分钟（delegate_task子代理）或30s-2分钟（CLI）
- **短审计范围成功率更高**：每轮只聚焦1-2个bug，不给AGY太多上下文
- **改完立即下一轮**：git commit后在同一上下文中启动下一轮，不等用户催
- **每轮commit一个"fix: AGY第N轮修复 — P0 xxx+P1 yyy"以便回滚**

## "持续最少100轮"的节奏估计

按3轮/会话、每轮耗时5分钟+修复10分钟的节奏：
- 一个会话可完成3轮（验证/修复/验证）
- 需要约34个完整会话达到100轮
- 实际会随着系统稳定性提升而收敛（一旦AGY签署终结，后续轮次只需要确认）
- 日常交易中发现的bug继续触发新的审计循环

## 关键教训

1. **先拉数据，再审计** — 不要在审计上下文里塞猜测。先拉orders/positions/trades + JSONL + cron输出
2. **AGY审计循环至少3轮** — 第1轮发现问题，第2轮验证+发现遗漏，第3轮全面确认
3. **3轮后可安全上线** — 第3轮AGY说"全部正确"和"未发现遗漏P0/P1"即可
4. **验证AGY结论** — AGY可能"过度审计"（指出不存在的漏洞），自己验证
5. **子代理比CLI更好** — delegate_task子代理更彻底（有文件+terminal工具），CLI只是纯AI
6. **🆕 用户找bug的响应旗帜信号**（2026-09-01 荣昌案教训）：
   - 用户说"为什么又买又卖XXX"或"不同任务逻辑相反" → 这是 **系统一致性危机**，不是小bug
   - 第一步永远不是自审修复，而是**拉数据**（交易记录、cron输出、JSONL候选）给用户看"事实是X"
   - 第二步**检查的不是方向冲突检测而是底层分析逻辑**：同一30根K线为何两脚本出相反结论？
   - 三步对话法：**事实→根因→方案**，不要绕过"根因"直接"方案"

7. **🆕 策略级转向信号**（2026-09-01 R1-R10实战）：
   - 用户说"你一个连板股都没抓到"或"最应该思考的是赚钱" → 这是 **策略方向的根本否定**，不是bug
   - 响应模式：**立即停止所有修复 → 启动10轮战略级AGY审计**
   - 核心区别：P0/P1修复不改策略（只改实现），策略级转向**改策略本身**
   - 典型例子：R1-R10中，不是修补现有的缠论+尾盘清仓，而是**废除策略+新建策略**
   - 100轮的节奏要求：策略级转向每次触发新的10轮循环，P0/P1修复每次触发3轮循环。100轮的本质是**持续迭代60-90轮P0/P1修复 + 若干次策略转向**

8. **🆕 AGY 审计自己修改的场景**（2026-09-07 修复审计）：
   - 当用户说"让agy审计你今天的修改提交"时，是指让 AGY 检查我**今天自己的修复是否正确**，不是找新bug
   - 审计上下文应包含：git diff + 修改说明 + 我当时为什么这么改 + AGY要检查的5个具体点
   - AGY 在这种场景下的价值是发现**自审盲区**：本次自认为"加好了elapsed/t1/t2/t3" → AGY 发现 Phase 1 的 `(target - now)` 冻结时间才是真正根因
   - 这种审计模式特别有价值：**改代码的人的盲区 = AGY 最擅长发现的东西**
   - AGY CLI 比 delegate_task 更适合此场景：不需要跑代码验证，只需要读 diff + 思考 + 出报告
