# 技术战法文档 → 持续候选生成器与买点触发器

## 适用场景

用户提供K线/涨停/突破类战法文档，并要求：

- 用它做全市场选股；
- 持续更新候选池；
- 买点出现时提示或进入自主交易链路。

核心原则：**完成单票识别脚本，不等于已经具备持续跟踪能力。** 只有候选生命周期、定时发现、警戒计划、盘中触发和风控执行全部接通，才能对用户说“已注册持续跟踪”。

## 一、先把战法变成可验证规则

1. 用文档解析器提取正文；图片中的K线条件必须逐图识别。
2. 区分：
   - 原文明确条件；
   - 为量化而新增的阈值；
   - 为安全而新增的确认条件。
3. 审计术语错误、宣传性胜率、幸存者偏差、未来函数和不可成交假设。
4. 每个形态至少输出：

```json
{
  "pattern": "放量过顶",
  "confirmed": true,
  "grade": "A",
  "trigger": 10.80,
  "invalidation": 9.90,
  "reason": "放量长阳收盘突破平台前高"
}
```

5. 形态命中只代表候选，不直接授权下单。

## 二、持续候选池的最小数据契约

候选池建议放在独立策略目录，例如：

```text
~/.hermes/trading/<strategy>/candidate_pool.json
~/.hermes/trading/<strategy>/runs.jsonl
```

候选记录至少包含：

```json
{
  "symbol": "600001.SH",
  "name": "中文名称",
  "sector": "行业/题材",
  "pattern": "放量过顶",
  "grade": "A",
  "score": 78.5,
  "trigger": 10.80,
  "invalidation": 9.90,
  "status": "armed",
  "first_seen": "YYYY-MM-DD",
  "last_seen": "YYYY-MM-DD",
  "expires_on": "YYYY-MM-DD",
  "source": "strategy_full_market"
}
```

### 状态机

- `armed`：当次扫描仍命中，允许写入盘中警戒计划；
- `watching`：历史命中过，但当次不再满足完整形态，保留观察但不得新增买入警戒；
- `triggered`：价格已命中，仅进入实时复核；
- `blocked`：触发后被市场、板块、资金、新闻或风控阻断；
- `executed`：具备 order_id 且完成订单回查；
- `expired`：超过有效期或结构失效，不再监控买入。

同一股票可命中多个形态，候选主键应使用：

```text
symbol:pattern
```

不要只按股票代码覆盖，否则会丢失不同形态的独立证据。

## 三、发现范围与数据源容灾

### 盘后全市场发现

推荐顺序：

1. 宽口径条件选股：非ST、非退市、流动性达标、近期出现过涨停/强突破；
2. 若自然语言选股空返回，使用涨停天梯或当日涨停归档作为确定性候选宇宙；
3. 对候选逐只拉取足够日线，运行形态识别；
4. 排序后只将有效候选写入池和警戒计划。

容灾不是放宽风控。不同数据源得到的候选，仍必须经过同一形态分类器、生命周期和风险门禁。

### 盘中刷新

盘中不必反复扫描全市场；重新扫描 `armed/watching` 候选即可，更新：

- 形态是否仍成立；
- 触发价与结构失效价；
- 状态与排序；
- 当日警戒计划。

## 四、警戒计划接入

候选必须写入统一的：

```text
trading/alert_plans/alert_plan_YYYY-MM-DD.json
```

计划示例：

```json
{
  "symbol": "600001.SH",
  "name": "中文名称",
  "source": "strategy_name",
  "direction": "buy",
  "status": "armed",
  "entry_rule": "突破并站稳触发价后复核量能、板块和资金；瞬时上影不买",
  "buy_alert": {
    "above": 10.80,
    "reason": "形态触发价"
  },
  "exit_rule": {
    "type": "structure",
    "stop_loss_structural": 9.90,
    "cancel_signals": [
      "跌破结构失效价",
      "突破无量快速回落",
      "板块退潮或重大利空"
    ]
  },
  "catalyst_type": "strategy_breakout"
}
```

写入时必须：

- 保留其他策略已有计划；
- 只替换本策略 `source` 对应的旧计划；
- 按 `symbol + direction` 去重；
- JSON临时文件写完后原子替换。

## 五、定时任务设计

推荐三个层次：

1. **盘后发现任务**：收盘数据稳定后运行全市场扫描，更新次日候选池；
2. **盘中刷新任务**：上午、下午各一次，重新计算候选状态和价位；
3. **统一高频守护器**：每5分钟读取警戒计划，负责触价，不为单一策略重复创建新的高频cron。

时序必须避开已有高负载任务和同分钟冲突。脚本型任务使用 `no_agent=True`，正常无信号时本地静默；只有触发、阻断或异常才通知用户。

## 六、触发后不是立即买入

触价后必须重新拉取：

1. 实时行情与分时承接；
2. 量能是否有效；
3. 板块梯队/主线是否共振；
4. 主力资金与筹码结构；
5. 新闻、公告及重大利空；
6. 市场情绪与仓位门禁；
7. 风控审批、intent注册、下单与订单回查。

正确链路：

```text
armed候选
→ 价格触发
→ 实时证据复核
→ structured candidate
→ risk
→ approved intent
→ exec
→ order_id回查
→ 通知与归档
```

## 七、TDD与验收

先写失败测试，再实现。至少覆盖：

- 新候选正确建档；
- 同一候选更新但保留 `first_seen`；
- 过期候选变为 `expired`；
- A级形态优先于弱辅助形态；
- 只有 `armed` 候选进入警戒计划；
- 触发价、失效价、中文名和策略来源完整；
- 警戒计划可JSON序列化并保留其他策略计划；
- 容灾候选不能绕过统一门禁。

完成后必须同时验证：

1. 目标测试和相关交易管道联合回归通过；
2. 真实数据试跑得到非伪造的 `universe_count/pattern_hits/armed_count/alert_count`；
3. 候选池文件真实存在且字段正确；
4. 警戒计划中能找到本策略 `source`；
5. cron任务已启用且下一次运行时间正确；
6. 高频守护器确实读取该警戒文件。

## 八、用户可见状态措辞

必须准确区分：

- `仅供观察`：只有分析文字或候选报告；
- `已注册持续跟踪`：候选已进入结构化池和高频守护器输入；
- `触发但被风控阻断`：价格命中但未形成可执行候选；
- `已提交委托(order_id)`：下单成功但不等于成交；
- `已成交`：订单回查确认成交。

禁止在只有单票扫描器或纯文字预案时声称“会持续跟踪”。
