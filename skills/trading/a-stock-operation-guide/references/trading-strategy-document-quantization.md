# A股交易战法文档：提取、审计、量化与验证闭环

## 触发场景

用户上传 DOCX/PDF/图片版交易战法、课程或策略文档，并要求“全部处理”“完整分析”“落地成策略”时使用。目标不是只做摘要，而是完成：**内容恢复 → 规则化 → 审计 → 实现 → 测试 → 真实数据试跑**。

## 一、文档内容恢复

1. DOCX 优先使用 `python-docx` 提取段落和表格；同时解压 `word/media/`，不能只读正文，因为核心规则常在截图中。
2. PDF 先判断是否文本型；文本型用 PyMuPDF，扫描件再走 OCR。
3. 对每张图分别做视觉识别，提取：战法名称、原文条件、K线位置、量价约束、示例代码和日期。
4. 明确区分：
   - 原文明确规则；
   - 根据图形作出的合理解释；
   - 后续为风控而新增的现代化规则。
5. 输出提取统计：段落数、表格数、图片数及落盘路径，便于验证没有漏页。

## 二、规则结构化

每个战法统一拆成：

- 前置环境：市场周期、相对位置、此前趋势；
- 形态序列：按交易日排列的K线关系；
- 量能条件：放量/缩量的比较基准和比例；
- 确认条件：必须等收盘还是允许盘中触发；
- 触发价：只有突破什么位置才算成立；
- 失效价：跌破什么结构即取消；
- 适用边界：低位/高位、主升/反弹、10cm/20cm制度差异；
- 原文未定义项：不得替作者补写成“原始规则”。

把“漂亮、长期、低位、放量、快速”等主观词改成显式参数，但在报告中标明这是**量化解释**而非原文。

## 三、强制审计清单

逐项检查：

1. **幸存者偏差**：是否只列成功图例，没有失败样本？
2. **未来函数**：需当日收盘才能确认，却假设能按当日收盘成交？
3. **不可成交偏差**：一字板买不到、跌停卖不出是否被忽略？
4. **制度差异**：ST、主板、创业板、科创板、北交所涨跌幅是否混用？
5. **统计缺失**：胜率宣传是否给样本量、期间、手续费、滑点及失败定义？
6. **术语错误**：K线名称是否与传统定义位置相反？如低位长上影应优先核对“倒锤头”，不能机械称高位“射击之星”。
7. **退出缺失**：只有买点，没有止损、取消、减仓、持有期限？
8. **市场门禁**：原文说“大盘不好禁用”时，应转为可执行的周期/指数/炸板率条件。
9. **龙头定义不足**：最先涨停不等于龙头，必须补充梯队、封板质量、成交额、换手和承接验证。

经验性“90%以上成功率”等表述，没有完整证据时必须明确降级为作者主张，不能作为实证结论。

## 四、量化实现原则

1. 扫描器只生成观察候选，不直接下单。
2. 输出至少包含：`pattern`、`confirmed`、`trigger`、`invalidation`、`reason`、`grade`。
3. 只能读取当前及历史K线，禁止读取未来数据。
4. 当天收盘确认型信号，默认最早在下一交易日验证和执行。
5. 容易误判的单根K线必须增加次日确认；例如急跌后倒锤头，需下一日突破其高点。
6. 将大盘门禁独立实现，不把市场条件藏在形态函数内。
7. 返回空数组是正常结果；禁止为了“有票可报”降低条件或编造信号。
8. 接入正式候选管道前，还需复核板块梯队、实时量价、资金、筹码、新闻和风控。

## 五、TDD与验证

遵循 RED-GREEN-REFACTOR：

1. 先为每种形态编写最小阳性样本测试；
2. 至少再写：普通走势不报信号、弱市门禁阻断、需次日确认的反例；
3. 运行测试并确认先因模块/行为缺失而失败；
4. 实现最小检测逻辑；
5. 单测通过后，与已有涨停/候选管道做联合回归；
6. 最后调用真实K线接口试跑若干股票。

最终报告必须提供真实证据，例如：

```text
新增测试：10 passed
联合回归：21 passed
真实接口：3只股票各120根K线，当前均无完整信号
```

“无信号”在此处是经过扫描得出的结果，而不是未执行脚本时凭空下结论。

## 六、交付格式

至少交付：

- 完整提取文本；
- 图片识别后的八/若干战法规则；
- 审计报告；
- 扫描脚本；
- 自动化测试；
- 真实数据试跑结果；
- 运行命令与文件路径。

用户说“全部”时直接闭环执行，不再逐项询问。对话中给核心结论，同时提供完整报告文件；若用户要求全文在对话中展示，则必须读取后完整发送，不能只给路径。
