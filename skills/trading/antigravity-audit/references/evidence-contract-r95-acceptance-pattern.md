# 交易分析系统证据契约与 95 分验收模式

## 适用场景

用户要求“彻底修复并优化至 95 分以上”，且系统同时覆盖大盘状态机、涨停天梯、板块分析、个股证据门禁与实战打法输出时。

## 核心方法

### 1. 按数据边界拆成三个并行审计域

1. **市场状态域**：缓存新鲜度、核心指标缺失、指数暴跌优先级、部分行情补齐、非交易日落盘。
2. **天梯与板块域**：涨停制度、缺行情 fail-closed、缓存日期、连板字段、资金缺失语义、连续交易日去重。
3. **个股证据域**：日线/分钟线完整性、量价异常、新闻与基本面硬证据、分析来源、持仓 API 失败语义、打法是否虚构标的。

每个域先建立专属 contract tests，再修改代码。不要让多个 worker 修改同一文件。

### 2. 缺失数据必须保持“缺失”语义

禁止把缺失数据转换成具有业务意义的零值：

- 资金流缺失：`None + fund_flow_status=missing`，不是 `0.0`。
- 行情缺失：`is_valid_board=False`、`board_type=unknown`，不是一字板。
- 连板高度缺失：剔除或 fail-closed，不默认首板。
- 核心市场指标缺失：零仓 fail-closed，不进入状态公式。
- 持仓接口失败：显示“持仓数据不可用”，不能显示“空仓”。

下游展示层必须显式兼容 `None`。单元测试通过后，必须真实运行报告脚本；展示层的 `flow > 0` 一类比较往往只有实跑才能暴露。

### 3. 缓存新鲜度契约

有效缓存至少同时满足：

- `data_fresh is True`
- `source_date == 当前交易日期`
- `updated_at` 可解析且未超过 `ttl_seconds`
- 必需字段全部存在

任一条件失败：`fail_closed=True`、仓位乘数归零。旧缓存仅可标记为 `stale_cache` 展示，不能改写成今日 live 数据，也不能落盘污染今日缓存。

### 4. 单元测试必须隔离生产状态

真实 `breaker_state.json`、市场状态缓存和盘中熔断可能使单元测试按设计被阻断。正确做法：

- 保留生产熔断，不得清空状态迎合测试。
- 对只验证候选生成、资金门禁或评分逻辑的单测，monkeypatch：策略熔断未触发、盘中动态熔断未触发、市场状态健康且新鲜。
- 另保留独立集成测试验证真实生产状态确实能阻断 BUY。

这能区分“业务逻辑回归”与“生产防御状态正在生效”。

### 5. 验收必须同时覆盖四层

1. **静态层**：`compileall` / `py_compile`、`git diff --check`。
2. **契约层**：专属 contract tests 全绿。
3. **回归层**：交易目录全量测试全绿；排除无关子项目依赖时要明确测试边界，不能把外部项目收集错误误报为交易系统失败。
4. **运行层**：真实执行核心报告脚本和 MCP 账本查询，检查输出是否崩溃、虚构、错标来源或错误解释缺失值。

### 6. AGY 最终签署

大型审计 prompt 超时时，使用原子验收问题：列明已落地的核心契约、测试数量与真实脚本复跑结果，要求 AGY 只回答 `YES/NO + 唯一最大风险`。AGY 的 YES 是独立签署，不替代 Hermes 自己的测试与实跑证据。

## 评分建议

达到 95 分以上至少要求：

- P0 fail-open 为 0；
- 核心缺失数据不再被伪装；
- 测试与生产状态隔离；
- 全交易回归通过；
- 代表性实战脚本真实运行成功；
- AGY 原子复审签署通过。

不应仅凭“测试全绿”给 95 分；没有真实脚本运行和输出核验，最高只能视为工程候选版本。
