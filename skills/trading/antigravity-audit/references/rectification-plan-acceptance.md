# 整改计划验收：专项通过不等于全量通过

用于核验 `AUDIT_AND_RECTIFICATION_PLAN.md` 一类跨仓库整改计划。目标是避免“文档写完/专项单测通过”被误报为“系统全部改完”。

## 一、四层证据

每个整改项必须同时映射以下证据；缺一层只能标记为“部分完成”。

1. **计划条目**：原问题、验收标准、影响仓库与文件。
2. **实现证据**：具体函数、分支、数据契约和调用方；不能只看文档或测试名。
3. **专项测试**：先构造失败用例（RED），修复后通过（GREEN）。
4. **真实链路/全量回归**：运行代表性生产脚本及仓库全量测试，记录精确 passed/failed 数量。

结论分级：
- `完成`：实现、专项测试、实际链路、全量回归均通过。
- `核心整改完成但未全量验收`：计划直接相关测试与链路通过，但全量测试仍失败。
- `部分完成`：仅代码或专项测试通过，真实链路未验证。
- `未完成`：验收条件仍可复现失败。

## 二、跨仓库验收顺序

1. 分仓库检查 `git diff --stat`、`git diff --check`。
2. 按计划逐项建立“条目→代码→测试→实际命令”矩阵。
3. 运行聚焦测试，修复直接相关缺口。
4. 运行语法编译与代表性生产脚本。
5. 最后运行各仓库全量测试；不得用专项通过覆盖全量失败。
6. 报告必须给出精确数字，例如 `15 passed`、`296 passed / 9 failed`，并列出失败类别。

## 三、常见数据契约陷阱

### 1. TDX K线字段大小写与历史基准

真实返回常见结构为：

```json
{"Rows": [{"Data": "20260928", "Close": "41.38"}]}
```

解析器不能只支持 `data/rows/date/close`，应兼容 `Rows/Data/Close`。连续涨停推断还必须包含连续区间之前的一根基准K线，否则三根涨停收盘只能计算出两次涨幅，连板数少算1。

测试夹具应尽量复制真实返回形状，而不是自造一个生产接口从未返回的格式。

### 2. API Key额度熔断

对于 `401/429/次数已用完`：
- 记录同一Key连续失败次数；
- 达到阈值后冷却至下一个北京时间自然日；
- 当前轮询立即跳过已冷却Key；
- 成功请求清除失败计数；
- 测试覆盖“冷却后跳过”和“次日恢复”。

### 3. MCP重试要识别返回值错误

调用可能不抛异常，而返回：

```json
{"error": "temporary failure"}
```

重试封装必须同时处理：
- 抛出的瞬时异常；
- 字典中的 `error`；
- 明确的失败状态字段。

不得只在 `except` 中重试。

## 四、生产状态污染测试

交易系统测试可能读取真实 `market_regime.json`、熔断状态或最新天梯文件，导致本应测试某个局部分支的用例提前被生产熔断拦截。

处理原则：
- 单元测试 monkeypatch 健康依赖或使用临时状态目录；
- 独立集成测试保留真实生产状态验证；
- 不得清空生产熔断状态来迎合旧测试；
- 若失败原因是测试隔离不足，报告为“测试/环境耦合回归”，但仍计入全量未通过。

## 五、Before / After 报告模板

```markdown
整改项：<名称>
Before：<可复现失败、错误字段或缺失行为>
After：<代码行为变化>
专项证据：<命令 + passed数量>
实际链路：<命令 + exit code/关键输出>
全量状态：<passed/failed数量>
结论：完成 / 核心完成但未全量验收 / 部分完成 / 未完成
```

## 六、禁止误报

- 禁止因计划文档存在就宣布完成。
- 禁止因一组mock单测通过就宣布生产链路完成。
- 禁止隐藏全量测试失败，只报告专项通过。
- 禁止把无关历史失败说成“本次整改导致”，除非通过diff或最小复现证明因果。
- 禁止在未运行实际脚本时声称链路已验证。
