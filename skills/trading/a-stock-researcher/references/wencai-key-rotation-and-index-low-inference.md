# 问财备用 Key 热加载与次日指数低点推演

## 适用场景

- 用户在项目 `.env` 新增 `IWENCAI_API_KEY_N`，要求接入常驻 MCP 服务。
- 问财前序 Key 返回 401/429/“次数已用完”，需要验证备用 Key 是否真正进入轮询。
- 用户要求基于问财数据推演次日大盘低点，而不是泛泛判断涨跌。

## 一、备用 Key 接入的可靠模式

### 问题

常驻 Python 服务通常只在启动时加载一次 `.env`。用户追加新 Key 后，即使源码已支持该编号，旧进程的 `os.environ` 仍可能看不到它；错误信息会一直停在旧的最后一个 Key。

### 推荐实现

1. 把 Key 发现逻辑抽成独立纯函数，便于测试。
2. 每次发起问财请求时重新读取项目 `.env`，而不是只依赖进程启动时的环境变量。
3. 按以下顺序收集：
   - `IWENCAI_API_KEY`
   - `IWENCAI_API_KEY_2 ... IWENCAI_API_KEY_10`
4. 同一槽位中，现有进程环境值优先，`.env` 值作为补充。
5. 去除空值和重复 Key，但保持优先级顺序。
6. 401、429或“次数已用完”继续轮询下一 Key；非额度类 HTTP 错误应直接显式返回，避免掩盖接口异常。

### TDD 最小覆盖

- 旧进程环境仅有 Key 1~3，而 `.env` 新增 Key 4：应返回四个 Key。
- `.env` 存在空 Key、重复 Key：结果应过滤空值与重复值。
- 不在日志、测试输出或报告中打印 Key 明文，只报告数量、槽位和是否成功切换。

### Before / After 验证

必须用同一条问财查询做对照：

- Before：错误停在 `Key 3 failed (401/额度耗尽)`。
- After：服务重载新代码后，同一查询返回 `status_code=0`、`datas` 非空。
- 同时验证：单元测试、`py_compile`、`git diff --check`、MCP `/health`。

注意：若实现了“每请求重读 `.env`”，以后仅新增 Key 值无需重启；但首次部署这段新代码仍需重启旧服务进程。

## 二、次日指数低点推演框架

低点必须输出“基准区间 + 中枢 + 极端防守区”，不能伪装成单点精确预测。

### 数据清单

1. 问财：指数当日 OHLC、成交额、涨跌幅、MA5/10/20/60。
2. 问财：ATR、RSI、KDJ、MACD、BOLL、技术支撑位。
3. 问财：上涨/下跌家数、涨停/跌停家数、全市场主力净流入。
4. 结构化行情源：四指数实时收盘/最低价双源核验。
5. 日 K：最近20~60日低点和局部枢轴低点。

### 计算方法

以当日收盘价 `C` 和 ATR14 为基础，计算：

- `C - 0.25ATR`
- `C - 0.50ATR`
- `C - 0.75ATR`
- `C - 1.00ATR`

再与以下位置求共振：

- 当日最低价；
- 最近20日低点；
- 最近60日局部枢轴低点；
- 整数关口；
- 问财给出的中期技术支撑。

通常：

- `0.5~0.75 ATR` 与近期结构共振区，可作为次日基准低点区间。
- `1 ATR` 或更下方历史枢轴，只作为恐慌情景。
- 问财“支撑位”若远离现价，不应直接当作基准预测，应标记为失守近端支撑后的极端防守位。

### 情景输出

至少给三条路径：

1. 主路径：先下探基准区间，再技术修复。
2. 次路径：直接反抽至破位平台，承压回落。
3. 风险路径：关键整数关口失守且30分钟不能收回，测试极端防守区。

每条路径都应列触发条件，重点观察：

- 30分钟能否收回关键点位；
- 上涨家数是否恢复；
- 跌停家数是否下降；
- 主力资金流出速度是否收窄；
- 创业板/科创板能否同步止跌。

## 三、常见陷阱

- 只改循环上限，却不解决常驻进程看不到新 `.env` 值的问题。
- 报告里展示 API Key 明文。
- 只用问财单源，不交叉核验指数 OHLC。
- 把超卖等同于反转；RSI低只能支持技术反抽概率，不能推翻均线和MACD下降趋势。
- 把问财中期“支撑位”机械当成明日低点。
- 给一个精确点位却没有区间、情景和失效条件。
