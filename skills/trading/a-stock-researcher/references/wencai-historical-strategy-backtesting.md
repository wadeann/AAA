# 问财历史选股与策略回测可靠性

## 适用场景

- 使用 `wencai_search` 回测过去若干交易日的选股规则。
- 需要历史涨停池、行业、量比、换手率、成交额、MA、资金流等宽表字段。
- 问财返回成功但字段日期错位、候选异常为空或误用前一交易日数据。

## 核心原则

问财适合提供历史语义宽表和行业标签，但不能把“请求成功”视为“历史日期正确”。所有历史字段必须核验方括号日期，例如：

```text
涨停[20260925]
涨跌幅[20260925]
量比[20260925]
成交额[20260925]
ma50[20260925]
主力资金流向[20260925]
```

若请求目标日为 `2026-09-25`，却返回 `涨停[20260924]`，必须将该日期标记为不可用，禁止把前一交易日数据当作目标日样本。

## 推荐两阶段查询

复杂查询一次塞入过多字段，可能发生语义误解析、返回空表或日期回退。可靠模式：

1. **轻量基准池**：先查询 `目标日期 非ST 涨停股票`，取得代码集合并验证 `涨停[YYYYMMDD] == true`。
2. **宽表元数据**：再查询连续涨停天数、二级行业、原因、收盘价、成交额等。
3. **按代码交集**：宽表只保留轻量基准池中的代码。
4. 如果轻量查询没有精确目标日字段，整日 Fail-Closed，不用前日数据替代。

不要在历史涨停查询中额外堆叠不必要的“股票代码 股票简称”等自然语言片段；问财通常自动返回它们，显式追加可能被错误解析成筛选条件或其他指标。

## 本地硬过滤

即使问财查询语句已写入筛选条件，回测代码仍必须对返回值重新过滤：

- 非ST；
- 涨跌幅区间；
- 量比阈值；
- 换手率区间；
- 成交额阈值；
- 价格上限；
- 是否已涨停；
- 资金净流入是否明确为正。

不得仅依赖自然语言条件已被上游正确执行。

## 无未来函数边界

### 可以用问财日终历史宽表验证

- 某日最终涨停池；
- 最终连板数；
- 日终行业归属；
- 日终涨跌幅、量比、换手、成交额、MA和资金流；
- 次日起的日线MFE、MAE、止损、目标和持有期结果。

### 不能把日终数据冒充为盘中截面

- 10:15、11:15、14:15当时的封板状态；
- 卖一为0、封单金额、撤单速度；
- 当时炸板率；
- 截至当时的成交额、换手率和量比；
- VWAP回踩、缩量企稳、重新放量、3分钟收复；
- 真实可成交深度和滑点。

若缺少分钟历史数据，应明确标注为“日终代理回测”，不能宣称是盘中实盘胜率。

## 评价与消融

至少同时输出：

1. 生产规则代理；
2. 排除已涨停；
3. 资金净流入明确为正；
4. 去掉资金门禁；
5. 多组涨幅上限和量比阈值；
6. 固定风险止损与代码当前止损；
7. 全量候选与预先声明排序后的可执行组合。

强制保存正负样本、过滤原因、不可用日期和字段缺失率。两周样本只能发现方向和实现缺陷，不能据此宣称统计显著或直接提升仓位。

## 常见策略实现陷阱

- 查询涨幅上限覆盖涨停幅度，却没有显式排除已涨停股票。
- 资金字段缺失时 Fail-Open，并将“缺失”混入“正流入”样本。
- 止损公式使用 `min(入场×0.96, MA50×0.985)`，在MA50远低于现价时反而扩大最大亏损；若意图是最大亏损不超过4%，应使用风险不扩张的方向并单独回测验证。
- 输出文案声称“回踩VWAP、缩量企稳、重新放量”，但候选生成代码没有计算这些条件。必须区分候选发现与真实触发成交。
- 为所有宽表候选逐票拉K线，导致请求量爆炸；应先应用各配置的排序与名额限制，再只拉入选标的K线，并对查询结果做本地缓存。

## 验证清单

- API Key仅报告数量和槽位，不打印明文。
- 用真实查询确认 `status_code=0` 且 `datas` 非空。
- 对每个交易日核对返回字段日期。
- 不可用日期写入结果元数据。
- 回测脚本通过 `py_compile` 和 diff检查。
- 结果文件包含逐票证据、汇总、分组、消融及限制声明。
